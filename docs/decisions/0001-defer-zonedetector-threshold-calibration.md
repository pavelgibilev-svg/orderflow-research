# ADR-0001: Отложить калибровку порогов zoneDetector (recall-тюнинг) до после прогона

- **Статус:** Deferred / Backlog
- **Дата:** 2026-06-16
- **Область:** `src/strategy/zoneDetector.ts`, `config/strategy.default.json` (пороги детектора зон)
- **Связано с:** `docs/STAGE_1_PROGRESS.md`, `docs/PARTICIPANT_A_PROGRESS.md`, baseline-lock reconciliation порогов X/Y/Z

> Документальная запись. **Поведение детектора не меняется** — ни одного порога, ни одного
> ключа конфига, ни строки логики этот ADR не трогает. Это фиксация решения, а не изменение.

## Контекст
- На текущих порогах `zoneDetector` выдаёт **~десятки zones в день** (точное число — по
  результатам Части C; пока не измерено инструментально).
- Поступало предложение **намеренно ослабить пороги** до **1000–3000 zones/день** ради
  повышения recall детектора.
- Направление методологически верное в принципе (больше выборки → устойчивее статистика),
  но **преждевременное сейчас**: нет эмпирики, на которой принимать решение «насколько ослаблять».

## Решение
**Пороги в этой итерации НЕ трогаем.** Калибровка (recall-тюнинг) откладывается до после
боевого/исторического прогона.

## Обоснование
1. ~десятки zones/день сейчас → на **6+ месяцах истории это несколько тысяч zones**, чего
   достаточно для **первой итерации Tier-2 статистики**.
2. Ослабление порогов = **подгонка параметров**, требующая решений «насколько ослабить».
   Без эмпирики это гадание.
3. Решение об ослаблении принимается **ПОСЛЕ прогона, по данным**, а не до него.

## Триггер пересмотра (backlog)
- **ЕСЛИ** после 6-месячного прогона выборка мала **в нужном (целевом) режиме** → ослабить
  пороги и перепрогнать.
- **Порог «мала»: PROVISIONAL ~<500 zones в целевом режиме.**
  ⚠️ Число **НЕ закоммичено** — финализируется ПОСЛЕ того, как увидим фактическое
  распределение zones из Части C.

## Зависимости
- Триггер оперирует понятием **«нужный режим»** → для его оценки прогон (**Часть C**)
  **ОБЯЗАН** выдавать счётчик zones **в разрезе ПО РЕЖИМАМ** (а не только суммарно/в день).
- **Требование к инструментации Части C** (фиксируется здесь как зависимость, реализация — не
  сейчас): per-regime zone-count в выводе прогона. Без него триггер пересмотра неоценим.

## Вне скоупа (сейчас)
- Любые правки порогов и config-ключей в `config/strategy.default.json`.
- Любые изменения кода детектора и автомата: `zoneDetector.ts`, `featureEngine.ts`,
  `absorption.ts`, `liquidityEvents.ts`, `volatilityRegime.ts`, `zoneStateMachine.ts`,
  `types.ts`.
- Добавление инструментации/счётчиков — это **Часть C**, отдельная задача.

## Последствия
- Baseline порогов остаётся зафиксированным (см. reconciliation X/Y/Z); первый прогон идёт
  на текущих значениях.
- Когда появится фактическое per-regime распределение из Части C — этот ADR ревизуется:
  финализируется порог «мала» и принимается решение о recall-тюнинге (новый ADR со статусом
  Accepted/Superseded).
