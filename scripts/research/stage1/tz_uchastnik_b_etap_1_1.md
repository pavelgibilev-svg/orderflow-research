# ТЗ для Участника Б — Этап 1: Геометрия стакана + контекстные слои

## 1. Контекст и цель

Цель этапа — расширить feature space движка `orderflow-research` за счёт четырёх новых классов фич:

- непрерывные геометрические моменты стакана (масса, центр масс, дисперсия);
- динамика Open Interest;
- поток ликвидаций;
- funding rate + basis.

**Зачем.** Текущие фильтры строятся на тех же сырых данных, что и сами зоны (стакан → absorption/thinning → зона → absorption-фильтр зоны). Это создаёт зависимость «фильтр от того же шума, что и сигнал». Геометрия даёт новый угол на стакан; OI, ликвидации и funding — внешние слои контекста, которых сейчас в проекте нет вообще.

**Этап закрыт, когда:**
1. Python-прототип на тестовых данных даёт численно стабильные фичи.
2. Прошли ablation-тесты, доказывающие, что новые фичи несут информацию, не дублирующую существующие.
3. Передан JSON-эталон тестовых векторов Участнику А для cross-check c TypeScript-движком.

## 2. Что НЕ входит в этот этап (явно вынесено за скобки)

Эти вещи известны как проблемные, но чиним их позже:

- Магические константы в `absorption.ts` (·50, ·3, ·1.1) — фиксируем как known issue.
- Подключение `minTriggerScore` к гейтам — позже.
- Dynamic invalidation в TargetChecker (досрочное закрытие на встречной зоне) — этап 2+.
- Любое моделирование исполнения (queue position, slippage, fill assumptions) — этап 3+.
- Hawkes-процессы, volume bars, event-bars — пока остаёмся на 1-сек сетке.

Если в ходе работы возникает соблазн «заодно поправить» что-то из этого списка — фиксируем в отдельный issue и двигаемся дальше. Расползание скоупа убивает этапы.

## 3. Входные данные

**Площадка:** Bybit BTCUSDT perpetual.

**Файлы Tardis (gzipped CSV):**
- `bybit_incremental_book_L2_BTCUSDT_*.csv.gz` — инкрементальные обновления L2.
- `bybit_trades_BTCUSDT_*.csv.gz` — рыночные сделки (с флагом стороны агрессора).
- `bybit_derivative_ticker_BTCUSDT_*.csv.gz` — снапшоты тикера: Open Interest, funding rate, mark, index.
- `bybit_liquidations_BTCUSDT_*.csv.gz` — события ликвидаций.

**Окно данных:**
- Октябрь 2025: 10–12 числа (3 дня) — пост-ATH distribution, начало bear market.
- Июнь 2026: 2–6 числа (5 дней) — пост-краха 28 мая continuation, **funding флипнулся на положительный**.

Два разных рыночных режима по позиционированию. Использовать оба в фазе разработки. Формальное разделение «in-sample / out-of-sample» проводится на этапе 2.

**Рекомендация:** День 0 для первичного аудита и отладки формул — взять **2025-10-11** (середина октябрьского окна, развитая внутри-дневная торговля). На нём прогнать всё, что описано в §4 и §5. Только после успеха масштабировать на остальные дни.

### 3.1 Нюансы Bybit, которые надо учесть в коде

1. **Liquidations компрессированы.** Bybit публикует не более одного события ликвидации на сторону в окне ~100мс–1с, объём при этом «слипшийся». Реальный объём отдельной ликвидации не восстановим. В фичах использовать как **флаг** (было/не было в окне) + грубый суммарный объём, **не** как точечную метрику.

2. **OI обновляется редко.** Snapshot OI в `derivative_ticker` приходит с шагом ~5–30 секунд. Прямая sec-by-sec `ΔOI` даст много нулей и редкие шипы. Делать forward-fill + **скользящие** дельты на нескольких окнах (60с, 5мин, 30мин).

3. **Объёмы в стакане Bybit идут в BTC**, не в контрактах. Проверить на чтении первого файла; если придут в контрактах — пересчитать через `qty_step` инструмента.

4. **Timestamps в микросекундах** (Tardis convention). Привести к единому UTC timestamp в миллисекундах для align'а с 1-секундной сеткой.

5. **Tick size BTCUSDT на Bybit:** 0.1 USD (проверить в `instrument_info`, на всякий случай).

## 4. Расчётные фичи

Все фичи считаются на **1-секундной сетке** (для совместимости с существующим `featureEngine`). Все формулы — векторизованные, через NumPy/Polars, без циклов по тикам.

### 4.1 Геометрические моменты стакана

Для каждого snapshot стакана, отдельно для bid и ask стороны, в окне глубины `maxDepthPct` (по умолчанию 0.5% от mid):

**Масса (M)** — суммарный объём в окне:
```
M_side = Σ v(x_i)  для всех уровней i, где |price_i - mid| / mid ≤ maxDepthPct
```

**Центр масс (μ)** — взвешенное среднее расстояние от mid, в тиках:
```
μ_side = (Σ d_i · v(x_i)) / M_side
где d_i = |price_i - mid| / tick_size
```

**Дисперсия (σ²)** — взвешенная дисперсия распределения объёма:
```
σ²_side = (Σ (d_i - μ_side)² · v(x_i)) / M_side
```

**Edge cases:**
- `M_side == 0`: вернуть `{mass: 0, com: NaN, variance: NaN}` и пометить snapshot как `empty_book_<side>`.
- Менее 3 уровней в окне: вернуть с предупреждением (variance на 1–2 точках мусорная).

### 4.2 Непрерывный имбаланс — две версии (это эксперимент)

Партнёр предложил формулу `(M_bid · |μ_bid| − M_ask · μ_ask) / (...)`. У неё, скорее всего, перевёрнутая логика — дальняя ликвидность весит больше близкой (`d_i` в числителе монотонно растёт от mid), хотя для краткосрочного price impact важнее именно ближняя. Поэтому реализуем две альтернативные версии и выбираем эмпирически.

**Версия A: weighted by 1/(1 + distance) — близкая ликвидность весит больше.**
```
W_bid = Σ v(x_i) / (1 + d_i)
W_ask = Σ v(x_j) / (1 + d_j)
imbalance_inv = (W_bid - W_ask) / (W_bid + W_ask)
```
`(1 + d_i)` вместо `d_i` чтобы избежать сингулярности на лучшем уровне.

**Версия B: экспоненциальный decay (с настраиваемой шкалой).**
```
W_bid = Σ v(x_i) · exp(-d_i / λ)
W_ask = Σ v(x_j) · exp(-d_j / λ)
imbalance_exp = (W_bid - W_ask) / (W_bid + W_ask)
```
λ — scale в тиках, начать с λ=10. Дальше можно тюнить.

Дуэль между ними — см. §5.2.

### 4.3 Динамика Open Interest

**Шаг 1.** Forward-fill snapshot OI на 1-сек сетку:
```
OI_grid_t = последнее наблюдённое OI_raw в [0, t]
```

**Шаг 2.** Multi-window deltas:
```
ΔOI_60s_t  = OI_grid_t - OI_grid_{t-60}
ΔOI_5m_t   = OI_grid_t - OI_grid_{t-300}
ΔOI_30m_t  = OI_grid_t - OI_grid_{t-1800}
```

**Шаг 3.** Нормализация на торговый объём:
```
TradeVol_5m_t = Σ trades.qty за окно [t-300s, t]
ΔOI_intensity_5m = ΔOI_5m_t / max(TradeVol_5m_t, ε)
```
ε = 0.001 BTC, чтобы не делить на ноль на спящих окнах.

**Интерпретация (для документации, не для расчёта):**
- ΔOI > 0 + price ↑ → long open (тренд жив);
- ΔOI > 0 + price ↓ → short open (тренд жив);
- ΔOI < 0 + price ↑ → short squeeze (закрытие шортов);
- ΔOI < 0 + price ↓ → long capitulation.

### 4.4 Поток ликвидаций

В каждой 1-сек ячейке:
```
liq_long_qty_1s  = Σ qty по событиям, где side == "Sell" (long ликвидируется → market sell)
liq_short_qty_1s = Σ qty по событиям, где side == "Buy"  (short ликвидируется → market buy)
liq_any_flag_1s  = 1 если хотя бы одно событие в окне, иначе 0
```

Multi-window агрегации:
```
liq_long_60s, liq_long_5m, liq_long_30m
liq_short_60s, liq_short_5m, liq_short_30m
```

**Важно** (из-за компрессии Bybit): первично использовать **флаг наличия** и **относительные изменения** (например, `liq_long_5m / liq_long_30m`), не абсолютные объёмы.

### 4.5 Funding rate

Snapshot funding из `derivative_ticker` (поле `funding_rate` или эквивалент в Tardis). Расчёт:
```
funding_current_t   = forward_fill из ticker'а на 1-сек сетку
funding_24h_avg_t   = mean(funding_current) за окно [t-86400s, t]
funding_sign_flip_t = 1 если sign(funding_current_t) != sign(funding_24h_avg_t)
```

Использовать **predicted current funding** (часто обновляемое значение), не только расчётный funding (раз в 8ч).

### 4.6 Базис mark vs index

Из `derivative_ticker`:
```
basis_bps_t = (mark_price_t - index_price_t) / index_price_t * 10000
```

## 5. Эксперименты ДО передачи в TS

Эти эксперименты — проверка того, что новые фичи имеют смысл и стоят внедрения. Делаются в Python на дне 2025-10-11.

### 5.1 Ablation — корреляция со старыми фичами

Для каждой новой фичи (mass_bid, com_bid, variance_bid, всё то же для ask, imbalance_inv, imbalance_exp, ΔOI_*, liq_*, funding_*, basis) посчитать Pearson и Spearman корреляцию **со всеми существующими фичами движка** (orderflowImbalance, buyAbsorption, sellAbsorption, refillScore, thinningScore, liquidityVoid, depthBuckets).

**Критерий:** если новая фича имеет `|corr| > 0.85` хотя бы с одной старой — это переименование старой. Не внедрять, либо письменно обосновать почему она всё равно стоит того (например: проще считать в realtime, или лучше ведёт себя в edge cases).

Артефакт: `ablation_correlations.csv` с матрицей корреляций + текстовое summary, что внедряем и что отбрасываем.

### 5.2 Дуэль двух версий imbalance

На дне 2025-10-11:

1. **Разметить локальные развороты.** Точки, где `mid_price` через 60–300 секунд изменится более чем на 0.2% против предыдущего тренда (определить тренд как знак ΔP за последние 300с).
2. Для каждой версии imbalance посчитать среднее значение в окне 30с **перед** разворотом vs во всех остальных точках.
3. **Cohen's d** разделения.

**Победитель** уходит в TZ для Участника А. **Проигравший** — в архив с короткой запиской.

Если оба дают |d| < 0.3 — обе версии слабые, нужно искать другую формулу или отказаться от непрерывного имбаланса в пользу bucket-based.

### 5.3 Визуальный аудит (Alpha report)

Сгенерировать interactive HTML (plotly) с наложением:
- Линия mid price BTC;
- Heatmap изменения CoM bid (одним цветом) и CoM ask (другим);
- Маркеры событий ликвидаций (размер маркера = объём, цвет = сторона);
- Линия funding rate (на вторичной оси);
- Линия ΔOI_5m_intensity.

**Что искать глазами:**
- Перед локальными отскоками вверх — прижимается ли CoM bid к спреду?
- Перед отскоками вниз — прижимается ли CoM ask к спреду?
- Совпадают ли крупные ликвидации с разворотами?
- Меняется ли поведение между октябрьским режимом (negative funding) и июньским (positive funding)?

Если визуально паттерн не виден — формулы либо неверны, либо сигнал слабее шума на этих окнах. Возвращаемся в §4 и пересматриваем.

## 7. Acceptance criteria (Definition of Done)

Этап готов, когда **все** пункты выполнены:

1. **Numerical match.** Python и TS считают одинаково: 6 знаков после запятой совпадают на ≥ 50 000 строк с любого дня. Подтверждено автоматическим скриптом сравнения.
2. **Ablation passed.** Каждая внедрённая новая фича имеет `|corr| < 0.85` со всеми существующими, либо есть письменное обоснование почему она всё равно внедряется.
3. **Imbalance duel resolved.** Выбран один из двух вариантов (`inv` или `exp`), с цифрами Cohen's d в обосновании.
4. **Alpha report сгенерирован.** Plotly HTML со всеми слоями, просмотрен обоими участниками.
5. **Test vectors переданы.** JSON с ≥ 10 кейсами, покрывающими edge cases.
6. **Bit-exact parsing.** На референсном часе данных независимая реконструкция стакана (например, чистым pandas без оптимизаций) даёт identical L2 snapshot'ы с тем, что выдаёт быстрый Polars-парсер.
7. **README этапа.** Каждая фича: имя, формула, единицы, окно агрегации, edge cases — задокументирована.
